# Specifications

[← Back to docs index](../docs/README.md)

Every behaviour change in this repository starts here. Code is written from a
specification, not the other way round.

`docs/` describes **what the system is today**. `specs/` defines **what a change must
achieve** before it exists. Both are plain Markdown, readable and editable with any tool.

---

## One folder per issue

```
specs/<issue-number>-<kebab-case-title>/
├── spec.md     WHAT and WHY   — requirements, acceptance criteria. No stack, no file names.
├── plan.md     HOW            — technical approach, affected slices, risks.
└── tasks.md    IN WHAT ORDER  — checklist, each task citing a requirement id.
```

The folder number is the **GitHub issue number**, matching the branch convention in
[conventions.md](../docs/conventions.md):

```
issue            #52
spec             specs/52-learning-api-integration/
specs branch     52-specs-learning-api-integration
impl branch      52-frontend-implement-the-learning-api-integration
```

One issue, one spec folder, **two branches, two pull requests** — see
[Branches and pull requests](#branches-and-pull-requests) below.

## The loop

| Step | Produces | Done when |
| --- | --- | --- |
| 1. Specify | `spec.md` | Requirements numbered, acceptance criteria observable |
| 2. Clarify | `spec.md` | Zero `[NEEDS CLARIFICATION]` markers remain |
| 3. Plan | `plan.md` | Approach chosen, Constitution Check passes |
| 4. Tasks | `tasks.md` | Ordered, each task cites an `FR-` id |
| 5. Implement | code + tests | Every task checked, every acceptance criterion has a test |
| 6. Self-review | Phase 6 of `tasks.md` ticked | Every item passes. **The implementation PR is not opened before this** |

Steps 1–4 are cheap to review and cheap to throw away. Steps 5–6 are not. Reviewing a spec
is the point of the process — do not skip ahead to code because the change "looks small".

Two guards are deliberate, and they are the only ones: `/plan` refuses to start while a
`[NEEDS CLARIFICATION]` marker remains, and `/implement` refuses to open the pull request
while Phase 6 is unticked. Everything else may be revisited freely.

Each step has a slash command in `.claude/commands/`. They are a convenience, not the
process — the loop above is the process, and it holds whether you use them, another tool,
or none.

| Command | Does |
| --- | --- |
| `/specify` | Create `specs/<issue>-<slug>/spec.md` from the issue |
| `/clarify` | Resolve every `[NEEDS CLARIFICATION]` marker by asking |
| `/plan` | Write `plan.md` — only when zero markers remain |
| `/tasks` | Write `tasks.md` from the plan |
| `/implement` | Create the implementation branch, work the checklist in order, self-review, then open the PR |

**Exempt from the loop**, per [C-08](../docs/constitution.md#c-08--specification-before-implementation):
dependency bumps, CI configuration, formatting, and documentation-only changes.

The commands that read the API map (`/specify`, `/clarify`, `/plan`) **stop if
`docs/api-map.md` is missing**. It is generated by the backend and is not in place yet; a
hand-written substitute is the drift it exists to prevent. The first feature to hit this is
blocked until the map lands, and then it is never blocked again.

## Branches and pull requests

The specification and the implementation live on **different branches**, so a lead can
write a spec without starting a feature, and a developer can plan without committing to
build.

| Branch | Holds | Created | Pull request |
| --- | --- | --- | --- |
| `<issue>-specs-<title>` | `spec.md`, `plan.md`, `tasks.md` | By `/specify`, from `main` | Opened once the spec is clarified, so the spec is reviewed before the plan is written. Merges when `tasks.md` is done |
| `<issue>-<area>-<title>` | Code, tests, doc updates, ticked `tasks.md`, spec status | By `/implement`, from `main` after the specs PR merged | Opened only after Phase 6 of `tasks.md` is ticked |

Both branch names follow [conventions.md](../docs/conventions.md#branches). The specs PR is
documentation-only and therefore exempt from the loop it sets up (C-08).

## Rules

- **Requirements are numbered and stable.** `FR-001`, `FR-002`, … Once written, an id is
  never reused for a different requirement. Tests and tasks reference these ids.
- **`spec.md` never names a file, a library or a component.** If you cannot describe the
  requirement without naming `useQuery`, it belongs in `plan.md`.
- **Unknowns are marked, not guessed.** `[NEEDS CLARIFICATION: which error does an expired
  reset token return?]` — planning stops until it is resolved.
- **Every spec passes the Constitution Check.** Cite the articles in
  [constitution.md](../docs/constitution.md) that constrain the work.
- **Specs are not deleted.** A shipped spec stays as the record of what was agreed. Update
  it if the agreed behaviour changes; do not rewrite history to match what was built.
